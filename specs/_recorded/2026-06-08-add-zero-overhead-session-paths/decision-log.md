# Decision Log: add-zero-overhead-session-paths

Date: 2026-06-08

## Interview

**Q:** Should self-disable and profile swap be delivered in the same slice, or split?
**A:** Both in one slice — self-disable + profile codegen + MASTER swap together. Deliver the full +7.3ms→+0.5ms/0 story at once.

**Q:** When are `P_<hash>` profile scripts generated and dropped?
**A:** "Could it even create one on-demand? I am concerned that a permission is added to the config and refreshed, and then the script that was already set for a session is suddenly dropped."

**Q:** Is the preprocessor self-swap (a preprocessor issuing ALTER SESSION to repoint the session) feasible?
**A:** "Assume validated, but also keep in mind that after issuing the ALTER SESSION statement, the preprocessor also needs to be executed for the first statement."

**Q (amendment):** The original slice deferred orphan/cleanup of unused profile scripts. Should cleanup be in scope for this slice?
**A:** Yes — cleanup is now IN SCOPE, using a generational retire-then-reclaim strategy: never drop on the same refresh that orphans a profile (that race is unsafe); instead retire the orphaned profile to a bounce stub + stamp `orphaned_at`, and reclaim (physically drop) it on a later refresh once no active session could still be pinned. The "same-refresh drop is unsafe" reasoning from the original deferral is retained as the foundation of this design. See decisions [11]-[13].

## Design Decisions

### [1] Profile generation is eager (at refresh time) under admin context — not lazy/on-demand by MASTER

- **Decision:** Profile scripts are generated by `PREPROC.REFRESH_CORE.rebuild()` running under the `PREPROC_ADMIN` invoker context. MASTER never creates a profile script on demand.
- **Alternatives:** On-demand creation by MASTER when it first sees a user with rules; Python CLI generates profiles.
- **Rationale:** MASTER runs with INVOKER rights (ADR-001). An ordinary database user lacks `CREATE SCRIPT` in `PREPROC_RT`. Therefore MASTER physically cannot create scripts for that user. On-demand creation is impossible without architectural changes that would violate ADR-001. Python CLI is deployment-only per ADR-007. Eager generation at refresh time under the admin context is the only viable path.
- **Promotes to ADR:** yes

### [2] Never same-refresh drop — orphan cleanup is in scope via generational retire-then-reclaim (supersedes the earlier deferral)

- **Decision:** `REFRESH_CORE.rebuild()` MUST NEVER `DROP SCRIPT` a profile on the same refresh that orphans it. Orphan cleanup is now IN SCOPE for this slice (the product owner moved it in) via a generational retire-then-reclaim lifecycle: a refresh first *retires* a newly-orphaned profile (replaces its body with a bounce stub and stamps `orphaned_at`), and only a *later* refresh *reclaims* it (physical `DROP SCRIPT` + PROFILES row delete) once it is provably unpinned. See decisions [11], [12], [13] for the mechanism.
- **History (retained):** The original slice deferred all cleanup under a strict "never-drop" contract. The reasoning that a *same-refresh* drop is unsafe still holds verbatim and is the foundation of the new design: a session pinned to a dropped `P_<hash>` would fail every subsequent statement — a catastrophic lockout analogous to the enforced-mode grant-omission hazard in ADR-002. The user's interview response (decision [2] of the original log) expressed concern about exactly this race. The insight that makes cleanup safe now is generational: once a refresh commits a new RESOLUTION, no NEW session can acquire an old hash (MY_PIPELINE returns only current hashes), so the set of sessions potentially pinned to an orphan is fixed at orphan-time and only shrinks. Dropping is therefore necessarily deferred to a later generation — this is inherent to safety, not a limitation.
- **Alternatives:** Keep deferring all cleanup (unbounded profile-script accumulation); drop unreferenced profiles immediately (unsafe — the race above); replace with an inert tombstone and never reclaim (leaks PROFILES rows and scripts forever).
- **Promotes to ADR:** yes

### [3] MASTER dispatches statement 1 fully, THEN issues the ALTER SESSION swap

- **Decision:** On statement 1 in a convenience-mode session, MASTER: (a) reads MY_PIPELINE, (b) dispatches the statement through the full pipeline, (c) issues the ALTER SESSION pquery to swap/self-disable, (d) writes the transformed text via setsqltext. The swap is attempted after dispatch and before setsqltext.
- **Alternatives:** Issue ALTER SESSION before dispatching statement 1 (would skip statement 1's transformation); issue ALTER SESSION after setsqltext (no functional difference, but the ordering is cleaner when the swap pquery is before the final write).
- **Rationale:** The user's answer to the Q3 feasibility question explicitly stated "the preprocessor also needs to be executed for the first statement." Dispatch-then-swap satisfies this: statement 1 gets full pipeline treatment, and the swap takes effect for statement 2 onward. Ordering the ALTER SESSION before setsqltext is cleaner but functionally equivalent; both happen inside the same preprocessor invocation, which is not itself preprocessed. ALTER SESSION issued via pquery from inside the preprocessor carries no recursion risk (confirmed by the MASTER header comment at lines 40-41 of master.lua).
- **Promotes to ADR:** yes

### [4] profile_hash is computed in SQL at refresh time and stored in RESOLUTION; MY_PIPELINE surfaces it

- **Decision:** `REFRESH_CORE.rebuild()` computes `profile_hash` per user as an MD5 over the ordered `phase|ordinal|script_name|function_name|client_pattern` chain using Exasol's `HASH_MD5` SQL function. The hash is stored in `PREPROC.RESOLUTION` (new nullable column). `PREPROC_RT.MY_PIPELINE` exposes it alongside the existing columns. MASTER reads the hash from the single MY_PIPELINE result and uses it directly to name the target script — no Lua-side re-hashing.
- **Alternatives:** MASTER re-hashes the rule rows in Lua; store the hash in a separate per-user mapping table; expose via a separate view.
- **Rationale:** Lua-side re-hashing introduces a Lua/SQL hash-mismatch hazard (different hash algorithms, different encoding, different sort order). Storing in RESOLUTION and surfacing through the existing MY_PIPELINE view is the minimal change: no new objects, no new admin-table reads, compatible with the existing single-lookup design. The all-NULL sentinel for no-rule users (MASTER line 85) is preserved: NULL profile_hash in the no-rules row is the correct signal for the self-disable path.
- **Promotes to ADR:** yes

### [5] Mode gating: swap only in convenience mode; self-disable additionally requires self_disable_allowed

- **Decision:** MASTER attempts the ALTER SESSION swap only when `mode` is `convenience`. In enforced mode the swap is never attempted regardless of rules. Self-disable (the no-rule path) additionally requires `self_disable_allowed = TRUE`. Both flags are read from the single MY_PIPELINE lookup.
- **Alternatives:** Make self_disable_allowed the sole gate; skip mode check and rely on the engine to reject ALTER SESSION in enforced mode.
- **Rationale:** In enforced mode (`-alterSystemProhibitsAlterSessionForPreprocessing=1`) ALTER SESSION on the preprocessor is prohibited; issuing it would generate an error that MASTER would have to swallow. Mode is the system-level posture flag (the DBA controls it); self_disable_allowed is a second, deployment-level safety toggle. Both are read from SETTINGS via the existing MY_PIPELINE definer-rights view — no new admin-table reads needed.
- **Promotes to ADR:** no

### [6] Fail-open swap: any ALTER SESSION failure leaves the session on MASTER

- **Decision:** The ALTER SESSION pquery in MASTER is wrapped in `pcall`. Any failure — rejected call, missing target script, or any other error — is caught and silently ignored. MASTER continues with the existing dispatch result and writes the transformed text. The session remains on the full-lookup MASTER path for all subsequent statements.
- **Alternatives:** Raise on swap failure (would block the statement — violates ADR-004); log the failure (no logging mechanism in this Lua context without side effects).
- **Rationale:** The swap is a performance optimization layered on top of the existing safety contract (ADR-004). It MUST NOT weaken that contract. A failed optimization leaves the user in a correct but slower state; a raised error blocks user SQL. Fail-open is the only option compatible with ADR-004.
- **Promotes to ADR:** no

### [7] Profile script Lua body: baked static rule table, full MASTER semantics, no MY_PIPELINE call

- **Decision:** Each `PREPROC_RT.P_<hash>` script is generated Lua that hardcodes the user's resolved `(phase, ordinal, script_name, function_name, client_pattern)` chain as a static Lua table (a literal in the generated script body). The script reproduces the full MASTER dispatch logic: ALTER SESSION/SYSTEM guard, EXA_ALL_SESSIONS client lookup, `client_matches` literal-substring helper, per-rule pcall fail-open, EXPAND first-match-terminal, TRANSLATE → EXPAND → REWRITE phase order, setsqltext-on-change. It issues NO pquery to MY_PIPELINE or any admin table.
- **Alternatives:** Profile script calls MASTER with a static user-id hint; profile script re-reads RESOLUTION for the one user (still cheaper than MY_PIPELINE join).
- **Rationale:** The entire point is to eliminate the DB read per statement. A re-read of RESOLUTION would not achieve that. Hardcoding the rule chain in the script body is the only design that achieves ~0.5 ms/stmt (UDF VM load + static dispatch). The hash naming ensures the body is stable and idempotent: CREATE OR REPLACE always produces the same script for the same chain. The generated Lua mirrors MASTER's dispatch helpers exactly to avoid a semantic divergence hazard.
- **Promotes to ADR:** yes

### [8] Hash manifest includes client_pattern and ordinal, not just module@version.function

- **Decision:** The profile hash manifest is over the ordered tuple `(phase, ordinal, script_name, function_name, client_pattern)` for each row in the user's resolved chain, concatenated in ordinal order. `client_pattern` and `ordinal` are included because they affect dispatch behavior and must produce distinct profiles when they differ.
- **Alternatives:** Hash only `(script_name, function_name)` tuples; include only the module list.
- **Rationale:** Two users with identical functions but different `client_pattern` values on their rules dispatch differently (one rule fires for client A but not client B). Hashing only the function list would collide them onto the same profile, producing wrong dispatch for one user. Similarly, two users with the same functions in different ordinal order execute them in different sequences — a meaningful behavioral difference. The mission description already calls out "module@version.function" but the interview-derived design requires a richer manifest to avoid incorrect collisions.
- **Promotes to ADR:** yes

### [9] Domain path for the new feature: runtime/session-optimizer

- **Decision:** The net-new session self-optimization capability lives at `specs/runtime/session-optimizer`. A new `runtime/` domain is created to hold session-lifecycle and performance-path features that do not belong under `install/`, `dispatch/`, or `refresh/`.
- **Alternatives:** Under `dispatch/` (alongside audit-rewrite, command-expansion); under `install/` (because it affects install artifacts); under `refresh/` (because profile codegen runs during refresh).
- **Rationale:** The session-optimizer capability spans MASTER (runtime dispatch behavior), REFRESH_CORE (profile codegen), and install artifacts (DDL/view changes). No single existing domain captures its primary concern: eliminating per-statement overhead for established sessions. A `runtime/` domain names the session lifecycle layer clearly and provides a home for future session-lifecycle features (e.g., warm-VM reuse). Dispatch/install/refresh deltas are written as changes to the relevant existing features, not subsumed into a new location.
- **Promotes to ADR:** no

### [10] Profile codegen atomicity: CREATE OR REPLACE before COMMIT in REFRESH_CORE

- **Decision:** `REFRESH_CORE.rebuild()` runs profile script creation (CREATE OR REPLACE, pquery) and PROFILES table upsert inside the same transaction as the RESOLUTION DELETE/INSERT, and all of this commits in the single COMMIT at the end of rebuild(). Profile scripts must exist before the COMMIT that makes the `RESOLUTION.profile_hash` column values visible to readers.
- **Alternatives:** Generate profiles in a separate post-commit step; generate profiles first then rebuild RESOLUTION.
- **Rationale:** ADR-010 mandates single-commit atomicity for the RESOLUTION rebuild. A committed RESOLUTION row referencing a `profile_hash` whose script does not yet exist would leave MASTER in a state where it cannot swap a session (the target script is missing). The post-commit hazard is analogous to the enforced-mode lockout risk from ADR-002. Creating profiles before the commit and as part of the same transaction eliminates this. DDL in Exasol Lua (pquery CREATE OR REPLACE) is visible to subsequent pquery calls in the same session without requiring a separate commit.
- **Promotes to ADR:** yes

### [11] Generational retire-then-reclaim is the orphan-cleanup strategy; same-refresh drop is provably unsafe

- **Decision:** Orphaned profiles are cleaned up in two generations, both inside `REFRESH_CORE.rebuild()` under `PREPROC_ADMIN`, within the existing ADR-010 single-commit envelope. (1) **Retire:** on the refresh that orphans a hash (no current RESOLUTION row references it, and `orphaned_at` is still NULL), `CREATE OR REPLACE` its `P_<hash>` body with a retirement stub and stamp `PREPROC.PROFILES.orphaned_at = CURRENT_TIMESTAMP`. (2) **Reclaim:** on a later refresh, physically `DROP SCRIPT PREPROC_RT.P_<hash>` and delete its PROFILES row only when provably unpinned (criterion in [12]). Step order inside rebuild is fixed: fingerprint → DELETE/INSERT RESOLUTION → generate (real bodies for all current chains, clearing `orphaned_at` on re-adoption) → retire → reclaim → stamp SETTINGS → single COMMIT.
- **Why generational is mandatory, not a limitation:** A session can only be pinned to `P_<hash>` if it swapped to that hash while the hash was current — i.e. it logged in and ran its first statement before the refresh that orphaned the profile. Once a refresh commits a new RESOLUTION, MY_PIPELINE returns only current hashes, so no NEW session can ever acquire the old hash. The set of sessions potentially pinned to an orphan is therefore fixed at orphan-time and only shrinks as sessions end. A drop on the orphaning refresh itself cannot be proven safe (a just-pinned session is still active); a drop on a later refresh can. Generational deferral is inherent to correctness.
- **Why a stub instead of leaving the live body or dropping:** Leaving the old live body would keep dispatching stale rules to pinned sessions indefinitely. Dropping immediately is the unsafe race. The stub is functionally identical to MASTER (decision [13]): on the pinned session's next statement it re-runs the full resolve→dispatch→swap, transforming that statement under the now-current pipeline and re-pointing the session to the correct current profile or self-disabling it — so pinned sessions converge to current behavior on that very statement (no untransformed gap), and the orphan becomes reclaimable once those sessions drain.
- **Alternatives:** Same-refresh drop (unsafe); never reclaim / tombstone-forever (leaks scripts and PROFILES rows); a separate out-of-band cleanup job (adds an operational surface and a second place to get the race wrong — folding it into the atomic rebuild keeps one source of truth).
- **Mode interaction:** Retire/reclaim run in refresh regardless of mode (refresh is admin-invoked, DB-side). The stub's ALTER SESSION bounce only matters in convenience mode — profiles are only ever pinned in convenience mode (enforced-mode sessions never swap). The cleanup logic itself is mode-agnostic and safe either way.
- **Auto-refresh interaction (ADR-018):** Mutating control scripts auto-run rebuild, so retire/reclaim runs after every CONFIG mutation too. Accepted without a frequency guard: the added cost is a couple of dictionary reads (the unpinned-criterion query over `EXA_ALL_SESSIONS`, already read by master.lua) plus targeted DDL issued only when the orphan/retired set is non-empty. When nothing is orphaned and nothing is reclaimable, the phases are pure reads and issue no DDL. A frequency guard would add state and complexity for no measurable benefit at the expected mutation rate; revisit only if profile churn becomes high.
- **Promotes to ADR:** yes

### [12] Reclaim safety criterion: drop only when no active session logged in before orphaned_at

- **Decision:** A retired profile (`orphaned_at IS NOT NULL`) is reclaimable iff no active session in `EXA_ALL_SESSIONS` has `LOGIN_TIME < orphaned_at` — equivalently `orphaned_at <= MIN(LOGIN_TIME)` over all active sessions. If there are zero active sessions, all retired profiles are reclaimable. The check reads `LOGIN_TIME` from `EXA_ALL_SESSIONS`; refresh holds `SELECT ANY DICTIONARY` (ADR-005) and master.lua already queries `EXA_ALL_SESSIONS`, so this is within the existing privilege model. `LOGIN_TIME` is confirmed as the session-start column on the Exasol session system tables.
- **Rationale:** Any session that could be pinned to `<hash>` must have logged in before the refresh that orphaned it, hence before `orphaned_at`. If every active session logged in at or after `orphaned_at`, none can be pinned, so the drop is provably safe. The criterion is conservative on one axis only: a session that logged in before `orphaned_at` but was never pinned to `<hash>` (it had different rules) merely delays the reclaim — it never causes an unsafe drop. Delaying cleanup is acceptable; an unsafe drop is not. This trades cleanup latency for an absolute safety guarantee, consistent with the framework's fail-safe posture.
- **Alternatives:** Track exact pinned-hash per session (Exasol does not expose the session's current preprocessor script reliably for this purpose, and it would still race); reference-count pins (no atomic hook to decrement on session end); time-based TTL (arbitrary, can drop while a long-lived session is still pinned). The login-time criterion needs no new bookkeeping and is provably safe.
- **Promotes to ADR:** yes

### [13] Retirement stub re-runs the full MASTER-equivalent resolve→dispatch→swap for the current statement (no untransformed-statement gap); MASTER and stub share an extracted MASTER_CORE module

- **Decision:** The retirement stub is **functionally identical to MASTER**. On any statement, a session pinned to a retired profile re-executes the full resolve→dispatch→swap logic for the CURRENT statement, exactly like MASTER's first-statement path: (1) look up the now-current pipeline via `PREPROC_RT.MY_PIPELINE` (`MY_PIPELINE`); (2) transform the CURRENT statement correctly through that now-current pipeline (the triggering statement IS transformed — there is NO no-transform gap); (3) re-point the session via `ALTER SESSION` to the correct current target — the current `PREPROC_RT.P_<new-hash>`, or self-disable / MASTER as the current resolution dictates — so subsequent statements run on the right script. All of this runs under the existing safety contract: ALTER SESSION/ALTER SYSTEM control-statement guard (return early, unchanged, no swap), per-rule pcall fail-open, fail-open on the ALTER SESSION swap, and setsqltext-only-on-change.
- **Implementation choice (CHOSEN — extract a shared core now):** MASTER's resolve→dispatch→swap logic is factored into a shared importable module `PREPROC_RT.MASTER_CORE` exporting a `run()` function, mirroring the existing `PREPROC.REFRESH_CORE` shared-module precedent (`import("PREPROC.REFRESH_CORE", "rc"); rc.rebuild()` in refresh.lua and every mutating admin script). After extraction: MASTER's body becomes a thin wrapper that `import("PREPROC_RT.MASTER_CORE", "mc"); mc.run()`, and the retirement-stub body is the **same** thin wrapper. There is exactly ONE source of truth for the dispatch+swap contract, so MASTER and the stub cannot drift.
- **Rationale for extracting now vs. emitting a MASTER-equivalent stub body without extraction:** The owner requires the stub to behave exactly like MASTER. Two ways to satisfy that: (a) emit a stub whose body duplicates MASTER's dispatch+swap logic (a third copy after MASTER and the real `P_<hash>` bodies — re-introduces precisely the divergence hazard called out in decision [7]); or (b) extract `MASTER_CORE` so MASTER and the stub literally run the same code. Option (b) is CHOSEN: the `REFRESH_CORE` precedent proves the `import()` shared-module pattern works in this codebase, extraction removes (not adds) a copy of dispatch semantics, and "stub == MASTER" becomes true by construction rather than by careful codegen. The baked `P_<hash>` profile bodies remain a separate, intentionally divergent artifact (they bake a static rule table and issue no MY_PIPELINE lookup — that is their whole point per decision [7]); sharing the core with them is explicitly OUT OF SCOPE for this change.
- **Why this is correct for the orphaned-profile case:** A retired profile's session no longer has rules that map to the old hash. Re-running MASTER logic looks up the now-current pipeline, transforms the current statement under it (e.g. a fail-open-sensitive REWRITE policy rule is correctly applied, not skipped), and re-points the session to the correct current target — so the session converges to current behavior on this very statement, with no statement running untransformed.
- **Options considered:**
  - *Pass-through + bounce, accepting a one-statement no-transform gap* — **REJECTED by the product owner.** Silently running the triggering statement untransformed would skip that statement's pipeline (e.g. a fail-open-sensitive REWRITE policy rule), which the owner deems unacceptable even for a single statement.
  - *Re-run full MASTER-equivalent resolve→dispatch→swap for the current statement* — **CHOSEN.** No untransformed gap; the session re-points to the correct current target.
  - *Stub raises to force the client to retry* — rejected (violates fail-open ADR-004).
  - *Stub silently does nothing and leaves the session on the stale stub* — rejected (the session would never converge to current rules).
- **Consequence:** Because MASTER_CORE is extracted, MASTER and the retirement stub share ONE dispatch+swap implementation; any change to the dispatch+swap contract is made in exactly one place and is covered by one tested source of truth. The base MASTER task changes from "edit master.lua's inline dispatch+swap" to "extract MASTER_CORE + make master.lua a thin wrapper"; the stub-codegen task emits the identical thin wrapper (or literally points at MASTER_CORE). See plan.md Group 4 and Group 6 task reconciliation.
- **Promotes to ADR:** yes
